# Operations runbook

Operational procedures for running the Mere project — building and
deploying the docs site, managing merelang.org, deploying the
Cloudflare Workers. This is the "HOW", with the footguns called out.
Design rationale ("WHY") lives elsewhere.

Not published to the docs site (the SSG only walks `docs/`).

---

## Docs site: build & deploy

The site at <https://merelang.org/> is a static site generated by a
Mere program (`contrib/site/build.mere`) — the SSG dogfoods the
compiler.

### Local build

```sh
sh contrib/site/build_full.sh docs _site
```

This runs:
1. `contrib/site/build.mere` — markdown → HTML + `style.css` + `index`
   + `search.json` + `sitemap.xml` + `.nojekyll`, and copies
   `contrib/site/playground/*.{html,wat}`.
2. Regenerates the self-host playground `.wat` bridges (fmt / repl /
   tyck / compile) from their `.mere` sources.
3. `wat2wasm --enable-tail-call` on every playground `.wat`. The
   `--enable-tail-call` flag is REQUIRED — contrib demos with `while`
   / inner-lifted closures emit `return_call[_indirect]` (Wasm
   tail-call proposal). Without the flag, `wat2wasm` rejects them.
4. Copies `contrib/dom/dom.glue.js` next to the playground HTML.
5. Writes `_site/CNAME` = `merelang.org` (custom domain — see below).

Serve locally: `cd _site && python3 -m http.server 8765`.

### Auto-deploy

`.github/workflows/pages.yml` runs on push to `main`: builds via the
same `build_full.sh`, uploads `_site` as a Pages artifact, deploys
via `actions/deploy-pages@v4`. `build_type` is `workflow` (Actions),
NOT the legacy "deploy from branch".

### Transient deploy failures

The `deploy` job occasionally fails with
`Deployment failed, try again later.` — this is a GitHub Pages
platform-side transient, not a repo problem (the `build` job succeeds).
Fix: re-run just the failed job.

```sh
gh run rerun <run-id> --repo merelang/mere --failed
```

If it fails 2-3× in a row, wait a few minutes and retry — it always
clears. The next successful push also supersedes it.

### Link paths — why root serving works

All generated links are RELATIVE (`changelog.html`,
`playground/counter.html`, `style.css` — no leading slash, no `/mere/`
prefix). So the site serves identically whether at the old
`merelang.github.io/mere/` (project subpath) or the current
`merelang.org/` (apex root). Don't introduce root-absolute (`/foo`)
or `/mere/`-prefixed links — they'd break one context or the other.

`sitemap.xml` uses relative `<loc>` (suboptimal SEO, not broken —
a follow-up could bake in the absolute base URL).

## merelang.org: DNS + custom domain + HTTPS

Deployment topology (decided 2026-07-07):

| domain | serves | cloud |
|--------|--------|-------|
| `merelang.org` (apex) | docs site (GitHub Pages) | **grey (DNS only)** |
| `www.merelang.org` | → apex (GitHub auto-redirect) | grey (DNS only) |
| `pkg.merelang.org` | package registry (CF Worker) | orange (proxied) |
| `api.merelang.org` | snippet share (CF Worker) | orange (proxied) |

DNS is hosted at Cloudflare (nameservers `*.ns.cloudflare.com`).

### First-time setup (already done — reference for a new domain)

1. Add the domain to Cloudflare, change registrar nameservers to the
   two CF nameservers, wait for the zone to show **Active**.
2. Cloudflare DNS records, **grey cloud (DNS only)**:
   - apex: `CNAME  @  →  merelang.github.io` (CF CNAME-flattening
     makes an apex CNAME legal)
   - `CNAME  www  →  merelang.github.io`
3. `build_full.sh` emits `_site/CNAME` = `merelang.org` on every build.
   With the Actions-based deploy this file is **inert** until the
   custom domain is explicitly set in step 4 (verified: a deploy with
   the CNAME artifact but no repo config left `gh api .../pages`
   `cname=null` and the old URL served 200, no redirect). So it's safe
   to pre-stage.
4. Set the custom domain:
   ```sh
   gh api --method PUT repos/merelang/mere/pages -f cname='merelang.org'
   ```
   (or Settings → Pages → Custom domain in the UI). This makes GitHub
   route the domain + start Let's Encrypt cert provisioning.
5. Wait for the cert (minutes to ~24h). When ready:
   ```sh
   gh api --method PUT repos/merelang/mere/pages -F https_enforced=true
   ```
6. Verify (bypass any local DNS negative-cache with `--resolve`):
   ```sh
   IP=$(dig merelang.org +short | head -1)
   curl -sS -o /dev/null -w "%{http_code}\n" --resolve merelang.org:443:$IP https://merelang.org/
   ```

### ⚠️ FOOTGUN: apex must stay grey cloud (never orange)

GitHub Pages renews its Let's Encrypt cert every ~90 days via an
HTTP-01 challenge to `/.well-known/acme-challenge/`. If the apex is
**orange cloud (Cloudflare proxy)**, CF intercepts that path and the
renewal FAILS — the site keeps working until the cert expires, then
HTTPS breaks with no warning (a delayed landmine).

**Rule: apex + www stay grey cloud (DNS only).** Only the Worker
subdomains (`pkg.` / `api.`) go orange — those ARE Cloudflare Workers,
so they belong on CF's proxy anyway. The docs site loses nothing
meaningful (GitHub/Fastly already CDN it).

### Recovery: HTTPS broke after ~90 days

If `https://merelang.org/` starts serving cert errors:

1. Confirm the apex is grey cloud in Cloudflare (if someone flipped it
   to orange, that's the cause — flip back to grey).
2. Force GitHub to re-provision: clear + re-set the custom domain.
   ```sh
   gh api --method PUT repos/merelang/mere/pages -f cname=''
   # wait ~1 min
   gh api --method PUT repos/merelang/mere/pages -f cname='merelang.org'
   # wait for cert, then:
   gh api --method PUT repos/merelang/mere/pages -F https_enforced=true
   ```
   (Same off/on toggle as Settings → Pages → remove/re-add domain.)

### ⚠️ FOOTGUN: CNAME ordering

Set up DNS **before** activating the custom domain. If you set the
repo custom domain while DNS doesn't yet resolve to GitHub, the
`*.github.io/mere/` URL 301-redirects to a non-resolving `merelang.org`
→ live site broken during propagation. (With Actions deploys the
artifact CNAME alone is inert, so pre-staging the file is fine — it's
the `gh api ... cname=` / Settings step that flips the switch.)

## Cloudflare Workers: registry & snippet share

Two Worker samples live in `examples/`:

- `examples/cloudflare-worker-registry/` → `pkg.merelang.org`
  (package registry v0.1, read-only JSON API)
- `examples/cloudflare-worker/` → `api.merelang.org` (snippet share,
  KV-backed)

They are TEMPLATES in `examples/` today. Promote to their own repo
when running them as production services.

### Build + deploy a Worker

```sh
cd examples/cloudflare-worker-registry   # or cloudflare-worker
sh build.sh                              # main.mere → main.wat → main.wasm
node local_test.js                       # smoke test (no CF account needed)
wrangler deploy                          # needs wrangler CLI + `wrangler login`
```

### KV setup (snippet share only)

```sh
wrangler kv namespace create MERE_SNIPPETS
# copy the returned id into wrangler.toml's [[kv_namespaces]] block
```

### The async-KV ↔ sync-Mere bridge

Mere externs are synchronous; CF KV bindings are async. Two
conventions bridge them (see `examples/cloudflare-worker/worker.js`):
- **Pre-fetch (read)**: JS `await KV.get()` BEFORE calling the Mere
  handler, stashes the value in module scratch, Mere reads it via a
  `cf_kv_lookup ()` extern.
- **Outbox (write)**: Mere returns `kv_put:{key,value}` in its
  response JSON; JS honours it AFTER the handler returns via `KV.put`.

Request body follows the same "extern-not-JSON" convention (`cf_body
()`) to avoid double-escaping arbitrary text through the JSON envelope.

### What doesn't work on CF Workers

V8 isolate, no Node stdlib. Unavailable Mere externs: TCP
(`tcp_connect`/…), subprocess (`subprocess_run`), file I/O
(`read_file`/`write_file`), sync sleep (`sleep_ms` — `Atomics.wait`
disallowed on the isolate loop). Use `fetch()` for outgoing HTTP, CF
bindings for storage.

## Running the test suite

```sh
dune test              # run the tests available with the installed tools
dune test --force      # bypass dune's cache if a run reports 0 tests
```

The reported total depends on optional tools. The full suite with Node.js
and WABT (`wat2wasm`) includes the Wasm execution checks; a source build
without them runs fewer tests and reports the omitted checks. Use the full
CI environment when validating the README's test count.

The C compiler bundle also runs SIMD allocation fixtures and a generated-runtime
probe under full UBSan on Clang and GCC 14/15. Its three negative controls must
detect lost type alignment, block payload alignment and buffer-growth alignment.
Run `sh scripts/c_compiler_check.sh --emit <directory>` followed by
`CC=clang sh scripts/c_compiler_check.sh --check <directory>` to reproduce it.

CI (`.github/workflows/ci.yml`) runs the suite on ubuntu + macOS ×
OCaml 5.1 / 5.4 (4-matrix). Integration checks use the validated Ubuntu 24.04
image and run in nine parallel groups:
compiler, runtime, containers, web, conformance, downstream, coroutines,
RISC-V and RISC-V ownership. Each integration check runs once. Common tools
are installed in every group; QEMU and the RISC-V disassembler are installed
only in the RISC-V group. Network setup has bounded timeouts and retries.
Required-tool preflights derive each group's tools from its assigned gates;
global tool-count floors and the full workflow's gate wiring are still checked.
The complete-toolchain preflight controls run in the RISC-V group. A failed
group does not cancel the others. The required check
retains its name,
`Gates (cross-backend and differential)`. It passes only when the assignment
check and every group succeed. Failed, cancelled or skipped groups fail it.
The coroutine and both RISC-V groups require a memu checkout with the RV32
and RV64 runners; a missing oracle fails the group instead of reducing it to
native-only checks. Only the downstream group writes the compile cache.
Run `ruby scripts/ci_gate_check.rb --self-test` to validate assignments and
failure propagation after editing the workflow. Both `ci.yml` and `pages.yml`
must be green before a release.

The build matrix, integration groups, Pages and shared distribution build
allow up to 30 minutes for compiler setup and 15 minutes for dependencies.
Build, Pages and distribution jobs have a 60-minute limit; integration groups
retain their 90-minute limit.
Dependency installation uses `scripts/retry.sh`: one retry after five seconds,
with the second attempt's exit status preserved. Opam downloads have two
attempts. Cancellation and command lookup failures stop immediately.
Pages tool downloads and release transfers have individual limits;
the setup validator and its controls run in the gate-assignment job.

Linux jobs configure APT before OCaml setup, including the package downloads
made inside the setup action. The Azure Ubuntu archive alias is replaced by
the official HTTPS archive, with two retries and 30-second HTTP/HTTPS timeouts.
This covers direct source entries and the runner's `apt-mirrors.txt` or
`mirrors/*.list` files used through `mirror+file` source declarations.
Repository suites, components, signing keys and other mirrors are preserved.
The setup action's opam cache remains enabled. Compare actual setup step
durations and cache-hit messages when measuring changes: a cache hit does not
avoid the action's system-package installation. All 192 gates and all four
build configurations remain required.

The README execution gate runs in the containers group. It still forces the
full unit suite to derive the README's test count, executes the transcript,
and builds a newcomer's program outside the checkout. The separate full
unit-suite step remains in compiler. Moving the README gate changes where
these checks run; it does not remove either execution or reuse cached output.
The assignment validator pins its name, command and destination, and the
containers preflight requires dune for it.

The parity harness treats a plain `test/parity/<case>.expected` as a required
runtime oracle. Interpreter, C, LLVM and Wasm must execute successfully and
match its exact bytes; a backend refusal or Wasm tool skip fails that case.
Per-backend divergence pins and named refusals for other cases remain separate.
The factory, scope and pattern oracles also run in the hosted RISC-V boundary
checks at both widths.

The hosted RISC-V execution sweep has three required partitions:
`rv_exec_check.sh --corpus32` in coroutines, `--corpus64` in RISC-V ownership,
and `--contracts` in RISC-V. The default `--all` still runs both corpora and
every boundary case. Split modes require their emulator runners. The
partition audit in the containers group compares compiler invocations with
all-mode, including a refused C reference and a refused RV32 program. This is
a routing check; the three real emulator jobs retain the output comparisons,
known-difference freshness checks, bounds and named refusals. Compare complete
job durations when measuring the split; setup time is part of the result.

The Unicode normalization conformance gate uses two interpreter workers over
contiguous, disjoint slices of the complete vendored corpus. It checks every
case's six NFC/NFD assertions and compares the reassembled output in original
order. Input coverage, output counts, worker exit statuses and cancellation
are checked; orchestration controls run inside the same required gate.
Use `NORMALIZE_JOBS=1 sh scripts/normalize_conformance.sh` for a serial run
of the same corpus and assertions. Both modes print the ordered output digest.

The two formatter corpus gates, `fmt_comments_check` and `fmt_roundtrip_check`,
run in downstream. Each retains both its complete corpus run and poison run.
The assignment validator pins their names, commands and destination, and the
downstream preflight requires Perl for comment counts. The full unit suite
remains in compiler and README execution remains in containers.
All 192 gates, nine groups and four build configurations remain required.

## Self-host semantic verification

`scripts/selfhost_check.sh` rebuilds the CLI compiler in an isolated temporary
directory on every run. The pattern, pattern-visibility, logic and record
fixtures, plus aliases, polymorphic types, modules, annotations and qualified
constructors and declaration-time constructor scope, require their `.expected`
companions. Their combined 140 handwritten
lines must match the reference interpreter and Wasm, the self-host evaluator
under the interpreter and Wasm, and programs emitted by the self-host compiler
running on Wasm. Emission, assembly, runtime and missing-oracle failures fail
the gate, including when several paths agree on the same wrong output.

`scripts/selfhost_record_check.py` requires 61 invalid-source cases to fail
with the specified diagnostics on the reference, interpreted self-host typer
and compiled self-host typer. Same-shape schema replacement uses the reference
build check, since `-t` can answer a type while noting that the build refuses it.
A valid reordered record must still compile and
execute. Unrelated parse errors, successful commands printing an error, signals
and bare traps cannot satisfy a refusal. Both compiled routes also execute
50,000 logical tail calls without increasing stack or memory limits. This runs
inside the existing compiler-group gate; all 192 gates, nine groups and four
build configurations remain required.

The existing Wasm-size gate also runs `scripts/selfhost_browser_check.cjs` on
the actual generated HTML, DOM glue and optimized compiler. It executes all
140 oracle lines, refuses the same 61 inputs, clears stale WAT and recompiles
valid input after each failure on the same instance, with default memory and
stack limits. Host imports are explicit: missing imports cannot become stubs.
The CLI and browser gates also execute the standard-helper fixture and all
17 required compatibility cases, including transitive helper dependencies,
polymorphic calls and declaration-order shadowing.

CI, Pages and release builds populate the opam tool cache through the official
GitHub release API before running the pinned OCaml setup action. Downloads must
match the release's sizes and SHA-256 digests and pass detached GPG signature
verification against the setup action's expected primary key. The completion
marker is written only after verification and an atomic executable replacement.
The existing assignment gate checks bootstrap ordering and runs signature,
digest, interrupted-download and cache-publication controls. Compiler caching,
all 192 gates and all build configurations remain required.

Pinned Wasm, protobuf and gRPC oracle archives also use the release API. The
shared downloader checks release identity, size and SHA-256 before atomically
replacing an archive; older assets without digest metadata require a reviewed
SHA-256 pin in the workflow. Each API request has a 45-second timeout and at
most two attempts. The assignment gate checks failed and partial downloads,
wrong metadata and preservation of a previously verified destination.

The public installer tries official release API endpoints when browser release
redirects fail, including latest-tag resolution. Both binary and checksums stay
pinned to that tag. The existing SHA-256, version and program execution checks
still precede atomic replacement; API failures preserve an existing install.

## Binary releases

`release-build.yml` is shared by the distribution CI jobs and tagged
releases. Build the Linux x86_64 asset on Ubuntu 24.04 with OCaml 5.1; an
unversioned runner label must not change the distribution's build baseline.
Before uploading, `scripts/release_runtime_check.sh --linux <binary> <version>`
runs the same stripped binary on stock Ubuntu 24.04 and 26.04 images. It
checks the exact version, thread execution, a caught failure, and C/LLVM/Wasm
emission without installing additional packages. The macOS arm64 binary uses
the same build workflow and native runtime check. PR runs retain the checked
binaries as short-lived Actions artifacts for inspection.

Push a version tag only after verifying its source and release notes.
The Release workflow creates or reuses a **draft**, strips build metadata,
checks the binaries for credential patterns and home-directory paths, then
downloads the uploaded assets and checks their version and execution again.
After both binaries pass, it generates `SHA256SUMS` from the downloaded
assets and verifies the uploaded checksum file against them. The installer
uses this file, checks the version and runs a small program before replacing
an existing binary with a rename on the same filesystem.
A failed check leaves the release private. The workflow refuses to replace
assets on an already published release, including on a rerun.
Each downloaded binary must also match the staged bytes exactly and pass its
runtime checks again before the checksum job can run.

After the workflow and required CI checks pass, download both assets and
`SHA256SUMS`, verify the checksums, check their contents with the local
publication policy, and review the release notes. Publish the reviewed
draft explicitly:

```sh
gh release edit <tag> --repo merelang/mere --draft=false --latest
```

The asset checker detects known patterns; review remains necessary for
confidential material that a pattern cannot identify. Keep private detection
rules and review records outside the public source tree.
